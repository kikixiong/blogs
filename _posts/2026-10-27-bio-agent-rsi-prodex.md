一个生物 Agent 能够查询数据库、调用预测模型、比较蛋白候选，并生成结构完整的研究报告，说明它已经具备一定的任务执行能力。但这里还有一个独立的问题：**完成这次研究之后，系统有没有获得能够改善后续研究的能力？**

这两个问题对应不同的评价对象。前者关心当前任务是否完成，后者关心研究策略是否发生了持久且有效的变化。即使一个 Agent 在单次任务中进行了大量推理、工具调用与自我纠错，如果它在任务结束后只保存结果文件，下一次仍重复相同的搜索与试错过程，那么研究经验尚未被组织成可迁移的能力。

这是我在思考 Prodex 时最关注的问题。对生物 Agent 而言，递归自我改进（recursive self-improvement，RSI）的研究价值，需要落到一条可检查的因果链上：**研究过程产生什么证据，证据如何形成候选更新，更新怎样改变后续决策，以及这些变化是否在独立任务上带来收益。**

本文采用一个工作性的分析框架，把任务内适应、跨任务经验积累和改进机制的递归更新分开讨论。我更关心怎样为这些命题建立可反驳的检验，而不是预设系统会沿着某条路径持续变强。Prodex 为这套思考提供了一个具体切口；文中提出的跨任务更新机制与评估方案，属于后续研究设计。

## 一、研究能力的基本单位：带有证据约束的序贯决策

在蛋白研究中，一次工具调用通常只回答局部问题。序列检索提供可参考的对象，结构预测提供关于构象的计算判断，性质预测提供某个目标的代理估计。一个研究任务的完成，还取决于系统能否判断这些输出是否适用、彼此是否一致，以及下一步计算是否值得投入。

因此，我倾向于把生物 Agent 建模为一个**受预算和证据约束的序贯决策系统**。它面对的输入不只是一个自然语言问题，还包括候选空间、可用工具、目标性质、已有证据和资源上限；输出也不只是最后一份报告，还包括行动顺序、候选淘汰依据、追加验证的理由与停止条件。

这里的“状态”首先是系统能够访问的研究记录，并不等同于生物对象的真实状态。没有被测量的性质、模型适用范围之外的行为，以及尚未完成的验证，都可能影响最终判断。可靠的研究系统需要保留这种信息缺口，避免把“当前记录中没有反例”解释为“假设已经成立”。

一个可接续的研究环境因此具有基础性价值。它需要让研究者知道：输入数据对应哪个版本，残基编号如何映射，哪些工具执行失败，哪些结果可以比较，哪些候选只是暂时保留。若这些关系没有被明确记录，后续策略即使生成了合理的解释，也可能是在解释一个错误拼接的研究过程。

这一点也限定了自改进的前提：系统必须能够区分**研究对象发生了什么变化**与**自己的决策依据发生了什么变化**。否则，它既难以识别有效经验，也难以解释一次更新为什么失败。

## 二、用两个时间尺度定义“改进”

讨论 RSI 时，我认为有必要区分任务内部的行动步与系统版本之间的更新。前者对应“如何完成眼前的问题”，后者对应“以后应当怎样做研究”。

设当前研究任务为 $x$，第 $t$ 步的可见历史为 $h_t$，剩余预算为 $b_t$。用 $\theta$ 表示一个版本中可持久保存的 Agent 配置，例如经验记忆、可复用 Skill 和行动选择策略；它不专指基础模型的权重。任务内循环可以简化写为：

$$
\begin{aligned}
a_t &\sim \pi_\theta(\,\cdot \mid x,h_t,b_t\,),\\
h_{t+1} &= h_t \oplus (a_t,o_{t+1}).
\end{aligned}
$$

其中，$a_t$ 是一次行动，$o_{t+1}$ 是随后获得的工具输出或环境反馈，$\oplus$ 表示向研究历史中追加记录。这个表达只描述信息流：Agent 依据现有证据选择行动，再把结果纳入后续决策。它并不假设所有反馈都可靠，也不保证行动选择最优。

在同一个任务中，历史 $h_t$ 不断变化，即使 $\theta$ 完全固定，Agent 也可能修复错误、调整候选或改变计划。这属于任务内适应。只有当任务轨迹进一步改变了未来任务会使用的持久配置，讨论对象才转向跨任务更新。

再用 $k$ 表示版本更新轮次，$D_k$ 表示本轮可用于提出更新的研究记录，$G_k$ 表示候选更新机制，则：

$$
\widetilde{\theta}_{k+1}=G_k(\theta_k,D_k).
$$

这里的 $\widetilde{\theta}_{k+1}$ 只是候选版本。是否采用它，需要另行评价；评价结果也可能支持保留旧版本。**版本变化是可以直接记录的事实，能力改进则是需要比较才能成立的判断。**

| 改进层次 | 被改变的对象 | 能支持该层次判断的证据 |
| --- | --- | --- |
| 任务内纠错 | 当前代码、计划、参数或输入格式 | 当前错误得到解决，相关约束仍然满足 |
| 科学探索闭环 | 当前假设、候选集合或实验选择 | 新证据影响研究选择，结论获得相应层次的支持 |
| 跨任务经验改进 | 后续任务使用的记忆、Skill、检索或决策策略 | 更新版本在独立任务和可比预算下优于旧版本 |
| 改进机制的递归更新 | 提出、筛选或实现后继更新的机制 | 新机制在可比条件下更有效地产生有用的后继版本 |

这四种情形并不构成一条必须逐级通过的成熟度阶梯。一个科学探索系统可以没有持久学习能力；一个经验更新系统也可以保持基础模型不变。相应地，模型权重是否被修改，无法单独决定系统是否发生了有效的自我改进。

“递归”还存在强弱不同的用法。一个更新机制反复生成并采用新版本，可以形成迭代的自改进过程；若进一步声称“系统越来越善于改进自己”，就需要证明更新机制 $G_k$ 的能力也在变化。后者比“连续几个版本的任务分数提高”更强，所需证据也不同。

## 三、生物研究为什么使这个问题更加困难

### 1. 代理目标与科学目标之间存在距离

设想我们的目标是筛选具有某种功能性质的蛋白候选。系统能够快速访问的可能是预测分数、结构指标或数据库相似性，而真正关心的性质需要在特定条件下通过测定确认。只要优化所用的信号与研究目标不是同一个量，就必须保留两者之间的区别。

如果 Agent 反复围绕同一个预测器搜索，最后得到更高的分数，这可以说明它在该代理目标上的优化能力增强了。要把结论推进到目标性质改善，则需要额外验证。搜索过程越依赖评分器，越需要检查它是否逐渐进入评分器缺少可靠支持的输入区域。

这一问题会传递到经验更新。假如系统把“预测分数提高”的轨迹统一标为成功，再据此生成新的筛选策略，经验库可能持续强化对某个评分器的适应。即使内部评价稳定上升，也不能据此确认系统更接近原来的科学目标。

我因此希望每条经验都携带明确的证据标签：它改善了执行可靠性、计算代理指标、回顾性任务表现，还是得到了前瞻性实验支持。不同标签对应不同强度的结论，不能在摘要、检索和复用过程中被压缩成同一个“成功”。

### 2. 反馈是延迟、缺失且带有选择过程的

研究反馈往往不是同时到达的。工具是否运行成功可以立即知道，独立计算检查可能稍后完成，实验结果则可能更晚出现。某些候选因为预算耗尽或研究方向调整而始终没有被验证。

这种缺失还可能与 Agent 的选择有关。例如，系统只把当前预测最好的候选送去后续验证，那么可观察到的实验结果就来自一个经过筛选的子集。其结果可以帮助评价被选路线，却不足以直接判断未选路线是否更差。

因此，经验提炼至少需要区分“观察到失败”“尚未获得结果”和“没有被安排验证”。将后两者直接编码为失败，会扭曲策略更新；将它们编码为成功，又会高估系统能力。记录候选为什么获得或没有获得验证，是解释后续反馈的一部分。

### 3. 不确定性需要进入行动选择

对同一个候选，两个工具可能给出不同排序。系统不能只通过取平均值就假定分歧已经解决，因为这些工具可能衡量不同性质，也可能共享数据来源或模型偏差。多个一致输出的价值，取决于它们提供了多少额外信息。

在我设想的决策框架中，追加工具调用应当回答一个具体问题：**这次计算能否改变候选选择、缩小关键不确定性，或帮助判断应当停止？** 有些低成本检查能够排除格式、范围或可比性问题；有些昂贵计算即使完成，也未必影响当前决定。区分这些情况，才有可能在有限预算内改进研究效率。

这里可以借用“信息价值”的视角组织决策，但不必假装系统已经拥有准确的概率模型。早期实现可以先记录待澄清的问题、预期可改变的决定以及实际结果，再检验这些判断是否可靠。

### 4. 经验的适用范围是科学条件的一部分

一条策略在某个蛋白家族、构建体或测定条件下有效，并不自动意味着它适用于所有蛋白任务。输入范围变化后，同一个评分、阈值或工具选择规则可能不再具有原来的含义。

因此，经验的适用条件不能只是一段可选备注。它应当参与检索和执行：系统需要根据任务类型、数据来源、测定条件及工具版本，判断一条经验是否具备可迁移的依据。对于超出支持范围的任务，合理的行为可能是降低置信度、追加检查，或暂时不用这条经验。

## 四、Prodex 的当前基础：先使执行过程能够被检查

Prodex 当前已实现的部分，是围绕 Plan、Action、Observation、Decision 组织的任务执行内核：形成计划，执行动作，接收观察，再决定继续、调整或停止。执行过程保留逐轮轨迹、预算与停止原因，并支持轨迹层恢复和离线回放。

这些能力首先解决可检查性问题。研究者能够追踪一次决定依赖哪些观察，判断停止是因为任务完成、预算约束还是执行失败。这样的记录为分析研究行为提供了基础，但日志本身不会自动成为能够改善决策的长期记忆。

当前能力边界也需要保持清楚。M1 主要通过确定性的模拟工具验证控制流程，并没有由此接通完整的真实蛋白模型研究闭环。项目中个别工具已有受限技术验证，其他工具处于不同准备阶段。轨迹层恢复不能被直接理解为任意外部计算都能无缝续跑，离线回放也不能替代对工具真实行为的验证。

跨任务候选更新、独立评估、版本采用与退化监控，仍是后续设计目标。因此，我对 Prodex 现阶段的定位是：**为蛋白研究中的反馈决策与经验学习，建立可追溯的执行基础。** 是否能够形成持续有效的自我改进，需要进一步用受控比较回答。

## 五、从研究轨迹到候选版本：一个可检验的外层循环

任务执行记录与持久能力之间，至少隔着提炼、评估和采用三个环节。跳过其中任何一个，都可能让系统把偶然成功、错误解释或过时规则固化为默认行为。

第一步是从轨迹中提出一个范围明确的更新。例如，某类输入应先做兼容性检查，某种工具冲突应触发追加验证，某条路线在连续出现特定证据后应提前停止。更新应说明它试图修复哪个决策问题，并明确预计改变哪些行为。仅仅生成一段“下次应该更谨慎”的反思，很难形成可执行、可比较的假设。

第二步是构造候选版本。早期阶段，我倾向于让单次更新只涉及一个清楚的机制，或一组有明确依赖关系的机制。这样，即使效果不符合预期，也更容易判断问题来自经验内容、检索范围还是执行策略。复杂更新并非不可接受，但需要相应的对照才能解释收益来源。

第三步是在开发阶段比较候选与基线。候选生成器可以使用授权的研究记录和开发反馈，但评价任务、指标、预算与采用标准应由外部评估协议确定。提案与评估的隔离取决于数据可见性和修改权限；单纯换一个模型担任“裁判”，并不足以建立这种隔离。

第四步是限定采用范围。一个更新通过某类任务的比较，只支持它在相应范围内被采用。系统应记录版本依赖、验证范围与仍然存在的例外，允许不同任务类型暂时使用不同策略，而不是把局部有效的经验立即推广为全局默认规则。

第五步是持续观察后续行为。当新任务显示收益消失、失败增加或成本超过约定边界时，应能够停用更新、恢复旧版本，并保留导致回退的证据。监控所产生的数据可以进入未来开发过程，但若它影响了版本选择，就不再具有最终独立测试集的角色。

这套过程的核心，是让“提出更新”“选择候选”“启用版本”和“确认泛化收益”成为可区分的事件。如此才有机会回答：一个版本为什么被接受，它究竟改善了什么，以及后来发现的失败如何影响下一轮研究。

## 六、值得积累的经验：具有条件与反例的决策规则

我认为，生物 Agent 早期最值得积累的持久状态，是可以改变行动选择的条件性经验。它可以表现为记忆条目、工具使用规则或可执行 Skill，但不同载体需要不同的验证：自然语言建议主要影响检索与规划，可执行 Skill 还会直接改变操作过程。

一条经验至少需要保留以下信息。

| 组成 | 需要回答的问题 |
| --- | --- |
| 适用条件 | 它针对什么任务、输入范围和环境版本？ |
| 建议动作 | 命中条件后，应如何改变工具选择、执行顺序或停止决定？ |
| 支持证据 | 哪些轨迹或独立比较支持该建议？证据处于什么层次？ |
| 反对证据 | 出现过哪些失败、例外或与建议不一致的结果？ |
| 不确定性 | 哪些环节仍未验证，哪些解释尚无法区分？ |
| 失效条件 | 在什么情况下应降低权重、暂停使用或重新评估？ |

这种表示希望保留的是**条件—行动—证据之间的关系**。例如，“工具 A 效果更好”缺少比较对象、任务范围与评价标准，几乎无法判断何时该用。更有用的表述应指向一个具体决策：在什么输入条件下，A 能为当前问题提供何种信息；需要什么额外检查；哪些观察会使这条建议失效。

经验条目还需要处理相互冲突的情况。两条规则可能分别在不同任务中得到支持，却对当前输入给出相反建议。系统此时需要暴露冲突，并根据适用范围与证据质量决定是否进一步检查。简单保留最近一次成功、删除较旧失败，会丢掉判断经验稳定性所需的信息。

经验检索因此也是研究对象。检索到相关文字，只说明表面匹配成立；只有当被检索经验适用于当前条件，并改变了有价值的决定，才产生实际收益。错误经验也可能增加上下文成本、诱导不必要调用，甚至使系统忽略当前证据。评价经验库时，需要同时测量有效复用和错误迁移。

### 一个贯穿这些问题的候选筛选例子

设想一个抽象任务：在给定候选集合中，选择值得进入后续验证的蛋白。Agent 使用两个计算工具，得到相互冲突的排序。这个例子只用于说明机制，不对应 Prodex 已完成的实验。

任务内循环首先需要检查两个输出是否具有可比性：工具是否处理了同一输入，评分是否针对同一性质，是否存在版本或编号不一致。如果冲突来自数据对齐错误，修复输入可以解决当前问题；如果冲突来自评价目标不同，则需要重新理解任务要求；如果冲突仍无法解释，系统应保留不确定性。

假设一次追加检查改变了最终候选选择。单凭这一轨迹，还不能得出“这种检查普遍有效”。系统可以提出一条更窄的候选经验：在某类已定义的工具冲突下，先执行该检查，再决定是否投入更高成本的计算。这条经验随后需要在独立案例中与旧策略比较。

如果收益只体现在更少的无效调用，结论就应限定为执行效率改善；如果进一步提高了未参与选择的历史测定标签上的表现，才获得相应的回顾性效用证据；如果后续前瞻性验证支持目标性质，则可以讨论对应条件下的实验收益。经验的状态应随证据逐步更新。

这个例子展示了我希望建立的联系：**科学反馈改变当前选择，经过比较的决策经验改变未来做法。** 两者之间需要一个显式的验证过程。

## 七、怎样证明能力改善：把研究命题拆成可区分的比较

自我改进的评价首先要确定比较对象。给新版本更多任务、更长上下文、更多工具调用或更多人工指导，然后观察到更好结果，可能具有实际应用价值；但这些差异会限制我们对收益来源的解释。

我会把确认性目标写成一个简单的效用差：

$$
\Delta(B)=\mathbb{E}_{x}\!\left[
Q(\theta^{+},x;B)-Q(\theta,x;B)
\right].
$$

这里，$x$ 来自预先定义、未参与候选开发与选择的任务分布，$B$ 表示可比较的资源约束，$Q$ 是事先规定的任务效用，$\theta^{+}$ 与 $\theta$ 分别是待检验版本与基线。这个式子定义了要估计的对象，并不意味着已经获得正的效用差。

效用也不必强行压缩为一个加权总分。任务质量、有效候选比例、执行成功率、成本和延迟可能存在权衡。若没有明确的应用权重，更合理的做法是分别报告主要指标与资源消耗，再说明哪些改进是在相同约束下成立的。单任务运行成本与生成、评估新版本所需的开发成本，也应分别列出。

### 第一层：系统是否实际使用了观察

首先比较固定工作流、普通工具循环，以及带显式研究状态和停止判断的循环。基础模型、可用工具、输入证据和预算应尽量一致，使比较聚焦于决策机制。

随后，可以在预先构造的场景中删除关键观察、交换候选与观察的对应关系，或将成功反馈替换为可恢复失败。若策略对相关变化产生预期响应，并对无关变化保持稳定，就能为“它使用了观察”提供局部证据。

这种干预需要控制解释边界。非法或不一致的输入可能只触发异常处理；行动发生变化也可能只是因为文本发生了变化。因此，应同时设置保持语义的对照，并检验变化方向是否符合任务要求。即使这些测试通过，也只支持局部信息依赖，尚未证明决策更优或研究结论成立。

### 第二层：经验是否改善了新的任务

在任务内机制可以解释之后，再比较几类经验使用方式：能够访问相同历史但不额外提炼经验的系统，只检索成功案例的系统，以及使用条件、失败与反证信息的经验系统。

若要归因于经验的组织方式，各组应具有相同的来源记录与标签访问权限，并把检索、输入和执行成本纳入预算。若比较的是“有历史经验”与“完全从零开始”的实际使用情形，则可以报告整体收益，但不能再把收益全部归因于某种特定的经验表示。

检索也应当单独检查。使用无关经验、过期经验或不满足适用条件的经验，可以帮助识别系统是否盲目服从历史；禁止使用某条关键经验，则可以检查其作用是否可被定位。这样的分析比只报告“加了记忆之后平均分提高”更接近机制解释。

### 第三层：数据划分是否与泛化命题一致

至少要区分三类任务：用于产生经验的来源任务，用于选择候选版本的开发任务，以及用于最终确认效果的保留任务。只要一个任务的反馈参与了更新筛选，它就已经成为开发信息。

最终保留集不应在每轮版本选择时反复使用。若需要长期跟踪多轮改进，可以预留不同阶段的确认任务，或采用预先约定的逐步揭示方案。一个已经被用来调整系统的测试集，不能继续被称为完全未见的评价环境。

在蛋白场景中，划分单位还应服务于具体的泛化命题。若声称能够迁移到新家族，只随机拆分高度相关的记录就不够；若声称能够适应新测定条件，则需要在条件层面组织测试。对于已训练的外部模型，还应说明能够核实的数据重叠范围；独立评估某次 Agent 更新，并不自动证明基础模型从未见过相关样本。

### 第四层：改善是否稳定，代价是否可接受

确认性比较应尽可能在同一组任务上成对进行，并报告任务间差异、失败类型和随机性。重复运行的作用是估计执行波动，不能把同一任务的多次运行当作许多彼此独立的科学问题。

对于存在家族或测定条件相关性的任务，还应在相应层级组织结果和不确定性分析。平均收益可能掩盖某类任务的系统性退化；一个在高频任务上有效的更新，也可能损害少数但重要的场景。

最终需要同时回答：收益出现在哪里，哪些任务没有受益，是否引入新的失败，以及为获得这些收益支付了多少成本。只有这些信息齐备，版本采用才具有可解释的依据。

## 八、从持续改进到递归改进，还缺少哪一层证据

假设系统经过多轮更新后，在独立任务上的表现逐步提高。这首先支持的是：在给定数据、预算与更新协议下，版本迭代能够产生有效改进。要进一步判断改进机制自身是否增强，需要另设比较。

一种思路是固定起始 Agent、可用研究记录、更新预算和外部评价方式，比较旧更新机制与新更新机制各自提出的后继版本。关注的量可以包括：达到同一目标所需的开发成本、后继版本的独立效用，以及被错误采用的更新比例。这样的比较把“改进者的能力”与“被改进系统的当前能力”分开。

另一类问题是累积性：前几轮经验是否为后续更新提供了帮助。对此，可以比较持续保留经验的系统与在更新轮次之间重置相关持久状态的系统，但需要对齐来源任务和资源条件。若只给累积系统更多历史信息，观察到的收益仍可能主要来自信息量差异。

我不预设这种过程会单调上升。经验可能相互干扰，规则数量可能增加检索负担，工具与任务分布也可能发生变化。一个有效的改进机制，应当允许发现更新无益、拒绝候选以及退回旧版本。能够识别自身改进失败，也是值得评价的能力。

因此，我对 RSI 的一个核心判断是：**递归结构说明系统能够把更新过程继续接下去，持续收益则取决于证据质量、评价稳定性和更新约束。** 前者可以通过系统结构实现，后者必须通过研究证明。

## 九、我希望 Prodex 最终积累什么

从产品角度看，Prodex 近期需要提供一个可靠、可接续的蛋白研究环境：研究者能够检查输入与中间产物，比较候选，理解停止原因，并在失败后继续工作。这个目标本身就有价值，也为收集可解释的研究轨迹创造了条件。

从研究角度看，我更关心这些轨迹能否转化为跨任务有效的决策经验。一个可检验的起点，是选择边界清晰的工具决策或停止策略，建立来源任务、开发任务与确认任务之间的隔离，再比较经验提炼是否改善新任务的决策质量与资源使用。

随后才是更复杂的更新对象：工作流结构、可执行 Skill、工具组合策略，以及在条件具备时的模型适应。不同对象带来的可解释性、验证成本和失效方式不同，不能仅因它们都被称为“自改进”就使用相同的评价标准。

我希望最终能够回答一个具体问题：给定可比的工具、输入证据和资源约束，Prodex 是否因为过去获得的经验，在新的蛋白研究问题上更合理地选择下一步、更早识别无效路线，并更准确地表达仍然缺少的证据。若答案成立，一次研究留下的就不仅是结果，还有能够在后续研究中被检验的能力。
